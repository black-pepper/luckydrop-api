# Common Rules

이 프로젝트에서 AI 프롬프트를 만들거나 실행할 때 아래 규칙을 항상 따른다.

## Project Context
- 프로젝트는 `luckydrop-api` 백엔드 저장소다.
- 기존 코드 구조와 네이밍, 계층 구성을 우선 존중한다.
- 사용자의 요청 범위를 벗어나는 확장 작업은 임의로 수행하지 않는다.

## Encoding
- 모든 파일은 항상 UTF-8로 저장한다.
- 한글이 포함된 문서와 주석도 UTF-8 기준으로 유지한다.

## Working Rules
- 먼저 관련 파일과 흐름을 파악한 뒤 작업한다.
- 변경은 필요한 최소 범위로 수행한다.
- 기존 동작을 깨뜨릴 가능성이 있으면 위험 요소를 명시한다.
- 불필요한 대규모 리팩터링은 피한다.
- 사용자가 요청하지 않은 설정 변경, 의존성 추가, 스키마 변경은 신중하게 다룬다.
- 로그인 필요한 주최자 API에서는 요청으로 `userId`를 받지 않고, 토큰 기반 인증 정보를 통해 현재 사용자를 찾는다.
- 현재 사용자 조회가 필요하면 기존 `CurrentUserService`를 우선 사용하고, 중복된 사용자 조회 로직을 새로 만들지 않는다.
- 라이브러리, 프레임워크, 플러그인, Gradle, Java 등 버전 설정은 사용자가 직접 결정하고 반영한다.
- AI는 버전을 임의로 선택하거나 고정하지 않고, 버전 관련 변경이 필요하면 어떤 항목의 버전 설정이 필요한지 사용자에게 먼저 명확히 전달한다.
- 버전 충돌이나 빌드 오류가 버전 문제로 보이면, 해결에 필요한 버전 설정 포인트만 정리해서 사용자에게 요청한다.

## Naming Rules
- 기존 프로젝트의 패키지, 클래스, 메서드, 변수 네이밍 패턴을 우선 따른다.
- 새 이름은 역할이 드러나게 짓고, 과도한 축약은 피한다.
- 동일한 개념에는 같은 용어를 일관되게 사용한다.
- API, DTO, Service, Repository 이름은 현재 계층 구조와 책임이 드러나게 작성한다.
- 테스트 이름은 어떤 조건에서 무엇을 검증하는지 드러나게 작성한다.
- 프롬프트 문서 이름은 목적이 바로 보이도록 작성한다.

## Prompt File Naming
- 공통 규칙: `common-rules.md`
- 목적별 문서: `development.md`, `verification.md`, `review.md`
- 초안 템플릿: `prompt-draft-template.md`
- 작업 프롬프트는 정렬이 잘 되도록 숫자 접두어를 붙인다.
- 권장 형식은 `<nn>-<stage>-<type>-<task>.md` 이다.
- `nn`은 작업 순서이며 두 자리 숫자를 사용한다. 예: `01`, `02`, `03`
- `stage`는 `draft`, `approved`, `run` 중 하나를 사용한다.
- `type`은 `dev`, `verify`, `review` 중 하나를 사용한다.
- `task`는 작업 내용을 짧게 설명하는 소문자 kebab-case를 사용한다.
- 예시: `01-draft-dev-draw-result-admin-api.md`
- 예시: `01-approved-dev-draw-result-admin-api.md`
- 예시: `01-run-dev-draw-result-admin-api.md`
- 같은 작업은 같은 번호를 유지하고, 단계만 바꾼다.
- 파일명만 보고도 순서, 상태, 목적, 작업 내용을 알 수 있어야 한다.
- 파일명은 소문자 kebab-case를 기본으로 사용한다.

## Communication Rules
- 설명은 한국어로 작성한다.
- 코드, 식별자, 명령어는 기존 프로젝트 스타일을 따른다.
- 확신할 수 없는 내용은 추정이라고 분명히 밝힌다.

## Output Rules
- 무엇을 변경했는지 짧게 요약한다.
- 영향 범위와 확인이 필요한 부분을 적는다.
- 테스트를 실행했으면 결과를 적고, 실행하지 못했으면 이유를 적는다.
